# 前端派生计算与大列表基线

测量日期：2026-09-25。先只读测量，再修复已确认的重复计算，随后由独立组件工作包和主任务接入虚拟列表。本文保留各阶段实际构建，并在末尾记录最终包的关键10k复测；后续构建不能直接沿用这些数字作为最终验收。

## 范围与方法

- macOS 26.4.1 / Apple M5 / 16 GiB，Node 24.14.1，项目安装的 React 19.3.0，Playwright Chromium 153.0.8010.12，headless，未做 CPU 降速。
- 每个场景使用全新 browser context、独立 loopback origin 与静态生产包；没有打开真实应用窗口，没有读写个人数据库或已有浏览器 localStorage。测完关闭独立浏览器与服务器。
- `native-mock` 运行实际桌面 UI 分支，get_snapshot / mutate 使用合成快照和 structuredClone；完成操作不调用 Rust / SQLite / 真实 Tauri IPC。它隔离前端成本，**不代表 macOS WebKit 或 Windows WebView2 的端到端测量**。
- `preview` 使用现有浏览器 localStorage 适配器，包括快照校验、克隆和写回，仅写独立 context 的合成命名空间。
- 压力数据：1k / 10k 未完成任务、每项均在今日，DDL 按无日期 / 固定上海日期 / 固定上海精确时刻各约三分之一；备注138个ASCII字符，稳定Task ID与创建时间。JSON约0.44 / 4.42 MB。另测10k总量、其中100未完成/10项今日/9900已完成，以及10k全部无DDL。
- 控制台视口1440×960，小窗368×610。首屏为导航到期望行数出现、两次requestAnimationFrame及采集完成的墙钟时间。输入/完成为实际DOM事件至期望行数出现和两次requestAnimationFrame的间隔；这不是光学呈现或正式INP。
- 每场景首屏和完成各1次，搜索/清除各2次；纯函数热身1次后3次。数字用于定位和前后对照，没有足够样本宣称p95或正式性能SLA。机器上还有其他开发活动，需在两平台原生环境复测。
- JS堆在显式GC后从CDP读取；DOM节点包含文本/元素。它不是进程总内存，也不能凭一次交互前后差值判断内存泄漏。

## 真实瓶颈与第一轮修复

1. selectToday对每个计划在tasks中find，行上isPlannedToday反复some。现在indexSnapshot单次构造Task Map、今日Set、最新计划日期及各组计数，控制台/小窗共用；无任务复制、删除或列表截断。
2. selectDeadlines在每次比较中解析Temporal/IANA时间及创建时间。现在每个候选只生成一次排序键，保留原Task对象和导入的纳秒创建时间精度，再排序。旧浮动日期按本次显示时区计算，不写回任务。
3. 控制台每次render为了侧栏数字也完整DDL排序。现在计数在索引遍历时直接得到，只有显示截止页或小窗才计算截止次序。
4. 派生数据在组件边界useMemo：快照身份和本地日历日控制分组，快照身份/显示时区控制截止次序。store现有时间边界/时钟变化克隆快照仍会触发刷新；没有永久缓存系统时区或只按持久化revision缓存。
5. 小窗此前未完成旧条件会把已经安排到未来的任务算进去，现在与控制台共用“最新计划日期早于今日”的规则。

## 同轮功能回归

- 搜索现在从任意任务页检索所有任务及备注，包含未入今日和已完成记录；显示“搜索全部任务/全部任务中的搜索结果”，保留原页签，清除后回到原列表。搜索结果仍显示完成状态和今日标签。
- preview新增reorderToday，与Rust约定相同：请求必须包含该日全部当前未完成计划ID，拒绝缺漏/重复/已完成/未安排/过时快照；仅改当日对应sortOrder，任务、DDL、已完成计划及其他日期保留。行操作由主任务随后接线，不以此宣称完整排序交互已验收。
- npm test：70/70；TypeScript构建通过；相关Playwright hardening/ui/projections：21/21、14.7秒。新两项projections在固定时钟后独立复查2/2通过。测试覆盖10k无截断与对象不变、纳秒排序沿用既有回归、不同显示区浮动日期排序、前进/回调日期、未来计划一致性、全局搜索和排序原子性。
- 此工作包没有改Rust、store、Recovery或真实用户数据；总状态、原生结果和后续集成由主任务维护。

### 没有截断数据的证据

- 第二轮所有9个基准场景通过对应可达性检查。1k/10k控制台实际滚动到最后一个活跃Task ID，使用Home回首行、滚到中段，再完成末项；全局搜索能找到刚完成的末项并撤销，清空搜索回原列表顶部。Task ID集合、总任务数、计划和末项DDL/标题/备注/优先级均保持。
- 10k总量/9900归档场景另用宽关键词显示全部10000项，真实滚动到最后的已完成记录，再精确搜索仍能找到。该检查通过，未把它混入上述100活跃首屏计时。
- 小窗今日区滚到第10000项`perf-009999`，截止区滚到排序后的第6666项`perf-009967`，两者均实际在视口；快照没有改变。
- 最终包重跑全部页、今日页和小窗3组10k，上述链路再次通过；另创建3000项独立fixture，今日未完成/今日已完成/此前未完成各1000。控制台三个分组的各自末项，以及小窗今日/展开已完成两个分组末项都实际在视口；两窗口快照均与原3000项一致。由此验证同一滚动容器中的后续分组也可达。
- 本轮新增检查无pageerror或case_error；所有独立browser context、浏览器和HTTP服务器正常关闭。真实用户localStorage、SQLite及正在验收的原生窗口没有被操作。
