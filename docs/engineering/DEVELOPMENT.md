# 正常开发一个 App 的流程

目标不是先写满代码，而是每一阶段都拿到可以检查的成果，再进入下一阶段。这个项目最难的是窗口与多屏行为，所以要比普通清单 App 更早做系统验证。

## 本项目如何走完整流程

| 阶段 | 主要工作 | 产物与通过条件 |
| --- | --- | --- |
| 1. 理解问题、调查现有方案 | 明确学习场景，试查可直接用或改造的产品 | 同类调研；区分已确认、未确认；已完成案头调研，待实测 |
| 2. 定义第一版 | 写清用户动作、边界、暂不做的功能 | PRD、验收标准；双平台首版已确认，参数可试用调整 |
| 3. 交互原型 | 设计控制台与小窗的布局、切换、状态、错误反馈 | 两种界面的线框图/可点击原型；已有运行中的双窗口实现；原生矩阵仍待完成 |
| 4. 技术验证 | 做只有空控制台、边缘小窗和把手的两平台 POC | 悬停、焦点、窗口关闭/恢复、缩放、多屏、热插拔通过；决定复用还是自建 |
| 5. 工程初始化 | 锁定栈和工具版本，生成工程、测试与构建配置 | 两平台能重复构建启动；目录占位不算初始化完成 |
| 6. 按完整场景开发 | 先打通控制台新建大任务→入今日→小窗完成→两窗更新→重启，再补设置与恢复 | 只做独立任务；每个功能带适当验证，始终保留可运行版本 |
| 7. 测试与真实试用 | 自动化验证业务；真机验证系统窗口；连续学习场景试用 | 记录问题、修复、回归；不能把 Mac 结果代替 Windows |
| 8. 打包与分发 | 生成安装包，检查升级/卸载、签名和公证需求 | 对应平台安装验收、发布说明、备份/恢复说明 |
| 9. 维护迭代 | 记录用户反馈，管理缺陷、数据迁移、依赖升级 | 状态、待办、交接和 CHANGELOG 持续更新 |

先做一条可使用的完整路径，再扩展功能。不能把所有页面画完就宣布 App 基本完成，也不能用网页原型证明系统悬停、多屏和置顶有效。

## 现在处于哪里

工程已实现任务管理、回收站、备份恢复、分区与窗口偏好，正做内部试用质量与原生验收；实际检查和包以 [STATUS](../delivery/STATUS.md) 为准。B03候选实机评估已按自建决策延后，不再作为下一步。按 [ROADMAP](../delivery/ROADMAP.md) 和 [BACKLOG](../delivery/BACKLOG.md) 选择当前工作。

Mac 后续代码与文档固定在 `mac` 分支，跟踪 `origin/mac`。开始修改前运行 `git status --short --branch`，推送前再确认；不直接推 `main` 或自行合并。Windows开发机从 `main` 交接基线继续，共享提交通过比较和明确移植协调，见 [Windows交接](../delivery/WINDOWS_HANDOFF.md)。

## 环境与检查入口

实际栈为 npm + Cargo；提交 `package-lock.json` 和 `Cargo.lock`。CI固定 Node **24.14.1** / Rust **1.98.1**；平台前置条件按 [Tauri官方说明](https://v2.tauri.app/start/prerequisites/) 核对。Mac构建需要 Xcode Command Line Tools，Windows前置条件和PowerShell步骤见Windows交接。最低OS和架构支持仍需实际验收，工具安装成功不等于产品通过。

开发、测试与打包的可执行命令集中在 [桌面开发说明](../../apps/desktop/README.md) 和 `.github/workflows/desktop-checks.yml`。浏览器预览使用合成数据；原生验证用独立identifier和数据库，不能以个人库造测试任务。首次环境验收记录OS版本、架构、显示器布局/缩放、工具链版本。

Windows 需要 Windows 环境运行测试；CI 可以验证构建，图形会话/真机用于 hover、DPI、输入法和多屏测试。本地 Mac 开发完成不能自动推定 Windows 通过。

## 一次开发迭代的标准动作

1. 从 BACKLOG 选择一个依赖满足的事项，写清本次通过条件，状态改为 In progress。
2. 做最小的完整改动。需求变化先同步 PRD，重要技术取舍写 ADR。
3. 验证与改动相关的行为；失败就修复并复测。对文档只检查内容、链接与一致性。
4. 自查差异、错误处理、对现有数据和平台的影响。
5. 更新事项、STATUS、HANDOFF；可交付变化写 CHANGELOG。
6. 向用户展示可检查成果，并明确哪些平台/场景还没验证。

## 测试分工

- 领域测试：完成/撤销、计划引用、排序、跨日/时区。
- 存储集成：事务失败、迁移、重启、备份恢复；使用临时库和合成任务。
- 界面测试：编辑、菜单、状态更新；数量服从关键流程，不为覆盖率写镜像实现的测试。
- 原生手工测试：多屏、焦点、热插拔、全屏、IME、真实安装。用录像/日志记录证据。
- 发布检查：安装、升级后保留数据、退出、卸载策略与已知限制。

实现后的检查命令应该集中在这里及 CI，保持两者一致。任何文档中的“通过”都必须能找到命令结果或手工证据。

## 发布与维护

内部试用首先服务于真实学习场景，明确系统范围与未签名状态。公开分发前再完成签名、公证等实际分发要求，以及依赖归属、隐私说明、升级恢复策略。自动更新不是 MVP 前提，初期可以手动安装新版本，但必须保护旧数据。

重要数据格式改变先设计迁移和备份，再写功能。每次修复一类多屏问题，补入验收矩阵，避免以后反复踩同一个坑。
