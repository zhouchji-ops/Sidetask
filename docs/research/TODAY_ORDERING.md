# 任务顺序整理：实现与参考

更新：2026-09-28。当前范围为 R06 / R09：今日计划、全部任务与截止日期各自拖动排序。下方先说明当前扩展，再保留 2026-09-25 今日上下移动按钮与追加顺序修复的历史记录；历史测试数字不代表本次拖动功能的验收结果。

## 三列表拖动排序（2026-09-28）

控制台的今日、全部任务和截止日期提供行内排序把手，小窗的今日和截止日期使用同一组件与协议。拖动时显示插入线，靠近当前滚动区边缘自动滚动；只有在列表内松手且位置改变才提交一次。`Esc`、列表外松手、失去捕获/焦点或页面隐藏取消手势；指针开始时记录的版本或列表上下文改变也取消。排序把手支持 `Alt+↑/↓`，无需鼠标拖动；控制台今日仍保留上移/下移按钮。搜索、已完成和回收站不允许局部重排。

三份顺序独立：

| 列表 | 持久化与提交 |
| --- | --- |
| 今日计划 | `reorderToday {date, taskIds}` 修改当天活动计划的 `sortOrder`，不改变其他日期或已完成/删除计划 |
| 全部任务 | `reorderTasks {scope:"all", taskIds}` 保存 `Snapshot.taskOrder` |
| 截止日期 | `reorderTasks {scope:"deadlines", taskIds}` 保存 `Snapshot.deadlineOrder`，同一事务设 `Settings.ddlSort="manual"` |

全部任务的活动集合为全部未完成、未删除任务；截止日期另要求有 `dueDate`。两种新命令必须提交活动集合中的全部 ID，不接受缺失、重复、未知或不属于当前列表的 ID；同时校验手势开始时的快照修订号。持久化成功后才发布新快照，失败保留已提交顺序，不改变任务内容、DDL、完成状态或 Task revision。

DDL 保留日期/重要程度/手动三个模式；前两种模式可直接拖动并切到手动，再切回自动模式不会删除手动顺序。手动顺序不因时间经过或重要程度变化重新排列，标签与逾期判断仍按原截止信息计算。两个 ID 列表缺失视为空：全部任务沿用原数组顺序，手动 DDL 沿用日期顺序。已经记录的完成、回收站及暂时无 DDL 任务保留排序槽位；重排仅替换当前活动槽位，恢复后继续使用保留位置。未记录的活动 ID 追加到已有顺序后，未记录 DDL 之间保持原日期顺序。

SQLite 升为 schema 6，旧 schema 1–5 在备份成功后仅事务更新版本标记，不重编码 snapshot / placement；新备份命名为 `before-schema-6`。便携 JSON v3 保存两份顺序，继续读取 v1/v2，旧格式不允许携带非空的新顺序字段。恢复保留当前设备设置及 DDL 排序模式，排序数据按备份完整替换。具体兼容边界见[数据模型](../engineering/DATA_MODEL.md#schema-6-三列表手动顺序与便携-v3)。

当前回归代码覆盖列表独立、完整集合/旧版本拒绝、隐藏位置恢复、数据库迁移回滚、备份失败、重启和 JSON 恢复。鼠标/键盘、虚拟长列表、双窗与原生执行应按实际验证记录报告，不沿用下方历史测试结果。此次交互使用项目内 Pointer Events 与既有虚拟列表实现，没有引入拖动依赖或复制第三方代码。

当时工作包为 R06 今日手动排序与直接移出；软删除、全局快捷键和拖拽排序不在该阶段范围内。后续回收站与本次三列表拖动分别扩展了范围。

### 当时的规则

新增动作 `reorderToday { date, taskIds }`，通过现有 `mutate` 和快照 `expectedRevision` 提交。`date` 严格使用 YYYY-MM-DD；`taskIds` 必须精确包含该日已经安排且当前未完成的任务，不能缺失、重复或混入已完成、未安排、未知任务。

只给这些 DailyPlan 按传入次序写入 `sortOrder = 0..n-1`；Task 的标题、备注、DDL、完成状态和修订号均保持，其他日期与已完成任务的计划记录完整保留。原计划数组不重排、不移除，只变更相应顺序值。快照修订号在事务提交后正常推进。完成、加入、移出和排序发生交错时，旧快照提交失败并由现有 store 刷新，不能静默覆盖。

当时原生命令仅由控制台整理完整顺序；小窗共享顺序，并通过既有 `planTask` 直接移出。搜索过滤时不允许整理局部结果。UI 首轮采用上移/下移和移出；2026-09-28 扩展后两个任务窗口均可整理今日与 DDL，全部任务重排仍只允许控制台。

## 原生复验修复：重新加入必须位于末尾

300 项原生演练发现：移出留有顺序空洞后，原先用全部计划数量生成 `sortOrder` 会与已有值相同，重新加入不能可靠落到末尾；历史日期的计划数量也会影响新顺序。`createTask(addToToday=true)` 使用同一错误生成方式。

Rust `append_plan` 与浏览器预览 `appendPlan` 现在共用同一规则：**每次真正增加一个某日计划时**，稳定地按该日已有 `sortOrder` 排序，将该日编号整理为 `0..n-1`，新计划放在 `n`。正常值、空洞、重复值、接近/等于 JavaScript 最大安全整数都采用这条规则，不计算可能越界的最大值加一；相同值维持此前显示的相对顺序。

只改目标日期的顺序字段，不重排原计划数组、不改任务主记录、DDL、完成状态或其他日期的计划。已完成计划也保留相对顺序、只在这次追加规范化中更新编号；`reorderToday` 自身原有的“已完成计划字段不改”契约仍保持。重复加入已存在的同日计划不触发规范化，移出仍只删除同日引用。该次追加修复没有 schema 变更或自动启动清洗；历史重复值在下次相应日期追加时整理。

新增对等回归：Rust 2 项测试覆盖“重排→移出→再加入”及新建/已有任务各自的空洞、同值、最大安全值场景；浏览器 4 项同类回归同时确认其他日期、旧 Task 记录和原快照不变，第二次加入不再变计划。固定版本 Super Productivity 的稳定相对顺序工具与 MIT 许可已在本次修复再次阅读，仅参考行为，不复制实现。

## 回收站接入后的规则（2026-09-25）

本工作包之后接入单项回收站。reorderToday 的完整集合只包含当日未删除、未完成任务；回收站计划保留且不参与重排。新建/重新加入计划时，只稳定整理该日未删除任务的已有计划（含已完成），回收站与其他日期计划原样。恢复不改变原sortOrder，同键沿用稳定次序，因此不承诺绝对旧行号。数据与恢复契约见 [任务生命周期](TASK_LIFECYCLE.md)。
